# Running SanskritAI Translator locally

This scaffold was written without a Flutter/Dart SDK available in the
authoring environment, so none of it has been run yet. Follow these steps in
order the first time; each one is a normal, supported workflow, not a
workaround.

## 1. Install prerequisites

- **Flutter SDK** (stable channel) — this also gives you Dart.
  https://docs.flutter.dev/get-started/install
- **Dart Frog CLI**: `dart pub global activate dart_frog_cli`
- **MongoDB**: either a free Atlas cluster, or run one locally (the
  `docker/docker-compose.yml` file spins one up for you).
- An **OpenAI API key** (or configure another provider once implemented).

Verify:

```sh
flutter --version
dart --version
dart_frog --version
```

## 2. Backend: server/dart_frog_api

```sh
cd server/dart_frog_api
cp ../../.env.example .env
# edit .env: fill in MONGODB_URI, JWT_SECRET, OPENAI_API_KEY, OPENAI_MODEL, CORS_ORIGINS
dart pub get
dart_frog dev
```

This starts the API on `http://localhost:8080`. Smoke-test it:

```sh
curl http://localhost:8080/api/v1/health
curl http://localhost:8080/api/v1/version

curl -X POST http://localhost:8080/api/v1/translate \
  -H "Content-Type: application/json" \
  -d '{"text": "रामः वनं गच्छति।"}'
```

The translate call requires `OPENAI_API_KEY` and `MONGODB_URI` to be set —
without Mongo it will fail when the orchestrator tries to look up dictionary
entries. `/health` and `/version` work with no configuration at all.

Run the backend's tests:

```sh
dart test
```

(`packages/shared_models` has its own test suite too: `cd packages/shared_models && dart pub get && dart test`.)

## 3. Seed the dictionary (minimum viable data)

The dataset generator (spec §26, Phase 10) isn't built yet. Until then,
insert at least a few `sanskrit_words` documents by hand so word analysis
has something to ground against — e.g. via `mongosh` or MongoDB Compass,
matching the shape in spec §16 / `lib/src/repositories/vocabulary_repository.dart`.
Translation still works with an empty dictionary; word-level meanings/source
attribution just won't be populated until you do.

## 4. Flutter app: apps/flutter_app

The platform runner folders (`android/`, `ios/`, `web/`, `windows/`,
`macos/`, `linux/`) are **not** checked into this scaffold — they must be
generated by the Flutter SDK itself, once:

```sh
cd apps/flutter_app
flutter create --platforms=android,ios,web,windows,macos,linux --org com.sanskritai .
```

This is safe to run on an existing app directory: it only adds the missing
platform folders and will not overwrite `pubspec.yaml` or `lib/`.

Then:

```sh
flutter pub get
flutter run --dart-define=API_BASE_URL=http://localhost:8080/api/v1
```

- On Android emulator, `localhost` from your host machine is not the
  emulator's `localhost` — use `http://10.0.2.2:8080/api/v1` instead.
- On a physical device, use your machine's LAN IP.

Run the widget test:

```sh
flutter test
```

Run static analysis before committing:

```sh
flutter analyze
cd ../../server/dart_frog_api && dart analyze
cd ../../packages/shared_models && dart analyze
```

## 5. Docker (backend only)

```sh
cp .env.example server/dart_frog_api/.env   # fill in real values
docker compose -f docker/docker-compose.yml up --build
```

## Known gaps (see docs/BUILD_PHASES.md)

- No registration/login endpoints yet — JWT verification middleware and the
  password hasher exist, but there's nothing issuing tokens yet. Every
  auth-gated route (`/conversations`, chat history persistence) will 401
  until that's added.
- Vector search is a no-op stub (`NoOpVectorSearchService`) — retrieval
  context sent to the LLM is empty until Atlas Vector Search + an embedding
  pipeline are wired in.
- Samāsa (compound) classification always reports `unknown` — see
  `lib/src/nlp/samasa_analyzer.dart` for why.
- Dataset generator/validator/import scripts (spec §26) are not built yet.
- No CI workflow yet.
